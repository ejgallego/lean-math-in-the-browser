# Methodology: Lean 4.34.1 evaluation, 2026-09-28

This follow-up migrates the client to 4.34.1 and adds the compiled-Wasm baseline
through FIR's C/Emscripten tooling. The earlier reproduction and rc2 artifacts
remain historical evidence; these are fresh comparisons on one host.

## Build and qualification

- Native client and both VIR package sets build on Lean 4.34.1, commit
  `5045d0056413266e57c625dcd7c365b10e377c52`. Mathematical source definitions
  are unchanged and their kernel checks pass during compilation.
- The isolated FIR producer is local commit `4ae9445c3eb7a2ff72fec9a87d769c976f9ab11a`,
  based on upstream `a09c113d1` with only its toolchain pin changed to 4.34.1.
  FIR main and other owners' worktrees were not modified.
- All ten regular FIR artifacts are **byte-identical** to the earlier rc2
  artifacts. This release change did not affect their generated Wasm.
- The C/Emscripten module builds with Emscripten 5.0.3, the exact 4.34.1
  unthreaded Lean runtime, Init/Std and libuv archives, `-O3` and LTO.
  Wasm size is 1,330,189 bytes; SHA-256 is
  `3aab10cf9ef687b31929d5e7629226d6535558e7054b80bfd4fc9168433f97b2`.
  Setup receipts verify copied runtime/source/header/archive identities.
- C staging removes VIR metadata and the unnecessary `public import Lean`,
  retaining all definitions and kernel checks. The facade uses Lean's module
  format. This resolves compiler-library initializer dependencies without
  stubbing initializers. A prior attempt using `meta import Lean` still
  retained those dependencies and failed to link; its staging/logs are saved.
- Native, revised JS and new VIR packages pass all 40 reference inputs
  (120 results). VIR uses the original bundled release runtime, not a newly
  rebuilt 4.34.1 runtime; the package producer is 4.34.1. This is a documented
  version difference with direct correctness evidence, not a reason to stop.
- Regular FIR qualifies 37/40 inputs, with 148 checked successful calls.
  fib(1,000,000), fibBits(1,000,000) and 1,279-bit primality exceed the 30-second
  per-call bound. C/Wasm qualifies 39/40 inputs with 156 checked calls; only
  decimal fib(1,000,000) times out. Both checkers traverse forward and reverse
  input orders with immediate repeats on retained instances. No completed
  result mismatched. Timeouts are not assigned estimated running times.

The C adapter uses FIR's digest-verifying loader, copies text before releasing
Lean objects and reacquires the heap view after calls that can grow memory.
These are Node packages; this does not qualify browser behavior or establish
unbounded memory safety. The old deployed SDK/packages and original JS
baseline remain unchanged. The revised JS baseline retains the partition
BigInt internally for `partitionsBits`, avoiding its former decimal round trip;
all 40 revised JS results pass independent hashes.

## Measurement policy

The comparison selects the same ten inputs as the earlier FIR campaign, each
qualified again on the new packages. It runs native, handwritten JS, VIR,
regular FIR and C/Wasm in ten orders balancing each engine position and each
within-round predecessor pair. There are ten measured calls per engine/input.
Every measured result is validated against its independent reference hash
outside the timer. Larger unqualified inputs remain visible above rather than
being silently removed from the correctness coverage.

FIR/VIR/JS/C-Wasm receive one explicit warmup on retained instances. Each native
sample starts a fresh process, drops its first in-process call and validates
the second result; process startup is excluded. Native generated C still
contains `lean_apply_1` between the monotonic-clock calls. FIR includes its
diagnostic host adapter and rewind, VIR SDK decoding, C/Wasm argument parsing,
Lean decimal formatting, text copying and release, and JS text formatting.
These are usable-call boundaries, not perfectly identical internal phases.

Node 24.21.0 / V8 13.6.233.17-node.53, Linux x64, Ryzen AI 9 HX 370. No client
build or other client benchmark ran alongside this timing campaign. Background
load, CPU affinity, frequency and thermal state are uncontrolled. JS uses typed
arrays and its own BigInt implementation. Native and Wasm arithmetic libraries
also differ. Ratios compare implementations; they do not isolate a universal
interpreter overhead or prove statistical equivalence.

## Results

The [consolidated report](REPORT.md#five-backends-one-comparison) contains the
single comparison table and interpretation. All 500 measured results pass.
Medians use ten samples per engine/input; ratios use unrounded medians from
this campaign only. Load averages were 3.12/3.24/2.71 before and
3.06/3.12/2.75 afterward. The [derived summary](../bench/results/2026-09-28/4341/summary.json)
retains medians and min/max ranges; these are descriptive observations, not
confidence intervals.
